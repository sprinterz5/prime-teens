# PrimeTeens · бот ментора

Telegram-бот для летнего интенсива PrimeTeens (7–9 классы, Астана).

Что делает:

1. **Регистрирует ментора по номеру телефона** — номер сверяется с белым списком,
   и ментор автоматически подключается к своей группе со списком учеников.
2. **Напоминает о занятиях** — за 2 часа и за 15 минут, с программой дня из рабочей тетради.
3. **После занятия проводит опрос по исключениям** — 3–4 минуты на группу.
   Спрашивает только про тех, кого ментор отметил: кто отличился, у кого не шло,
   кого не было. Плюс двое под «прожектором» по ротации. Отвечать можно
   **голосовыми**: бот их расшифровывает.
4. **В конце курса отдаёт материалы** — все заметки за курс, разложенные по разделам
   характеристики, чтобы её написал человек. Пакетом: общий HTML, по файлу на ученика,
   сводная таблица в Excel, сырой JSON.

## Быстрый старт

```bash
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env
```

Впиши в `.env` токен бота от @BotFather (`BOT_TOKEN=`) и `DATABASE_URL` — тот же Postgres,
что у веб-платформы (Next.js в корне репозитория): БД общая, схему и миграции ведёт Prisma
(корневой `prisma/schema.prisma`), бот сам ничего не создаёт и не мигрирует — только
читает/пишет по обычному SQL (`app/db.py`, `asyncpg`). Локально это тот же
`DATABASE_URL`, что в корневом `.env`. Сама база поднимается из корня репозитория:
`pnpm db:dev` (embedded-postgres, без Docker) или `docker compose up -d` — параметры
подключения одинаковые. Перед первым запуском накати миграции: `pnpm prisma migrate deploy`
из корня. В git токенов и паролей нет и быть не должно — `.env` в
`.gitignore`. Дальше — двойной клик по `run.bat`, либо:

```bash
run.bat
```

### Запускать только так

`run.bat` существует не для красоты — прямой запуск файла на этой машине ломается
дважды.

**1. Не тот интерпретатор.** В системе `.py` привязан к
`C:\Python27\ArcGIS10.8\python.exe` — это Python 2.7, приехавший с ArcGIS
(видно по `assoc .py` и `ftype Python.File`). Он падает на кириллице в исходниках:

```
SyntaxError: Non-ASCII character '\xd0' ... but no encoding declared
```

Такого сообщения Python 3 не выдаёт вообще — в тройке UTF-8 в исходниках разрешён
по умолчанию, и PEP 263 требовать нечего. Увидел эту ошибку — значит, запустилась
двойка. Ассоциацию я не трогал: от неё может зависеть сам ArcGIS.

**2. Не из того места.** `app\main.py` — часть пакета, запускать надо `-m app.main`
из корня проекта. Иначе, даже правильным питоном:

```
ModuleNotFoundError: No module named 'app'
```

`run.bat` закрывает оба случая: сам переходит в корень проекта и вызывает
`.venv\Scripts\python.exe -m app.main`. Если venv или `.env` нет — скажет, что
именно сделать, а не свалится молча.

Руками то же самое:

```bash
cd C:\Users\begot\Desktop\prime-teens\bot
.venv\Scripts\python.exe -m app.main
```

Сам `run.bat` написан **только латиницей**, и это не небрежность: `cmd.exe` читает
`.bat` в OEM-кодировке, и кириллица в UTF-8 разваливает разбор самого скрипта —
проверено, первая версия сыпала `'иллице' is not recognized`.

Напиши боту `/whoami`, скопируй свой ID в `ADMIN_IDS` в `.env`, перезапусти бота —
теперь ты админ.

### Настройка курса (админ, один раз)

Три пути заводят одни и те же данные — группы, менторов, учеников — через один и
тот же импортёр, поэтому их можно смешивать и повторять сколько угодно: повторная
загрузка не плодит дубли, только добавляет и обновляет.

**Основной путь — Google-таблица.** Заказчик ведёт данные в Google Sheets; скрипт
`integrations/sheets_sync.gs`, вставленный прямо в таблицу (Apps Script), публикует
её как Web App (небольшая HTTP-ссылка), а **бот сам ходит по этой ссылке** раз в
ночь (`SHEETS_SYNC_HOUR` в `.env`) и по команде `/sync_sheet` — без вебхуков и
Google Cloud (бот на long polling без публичного адреса, но исходящий HTTP-запрос
наружу этого и не требует). Пул, а не пуш: первая версия пыталась слать файл боту
через Bot API, но так не работает — сообщение, отправленное от имени самого бота,
не возвращается ему через `getUpdates`. Пошагово — установка, деплой Web App,
что за экран «приложение не проверено» и как через него пройти — всё в
`integrations/README.md`.

**Запасной путь — файл `.xlsx`.** `/template` пришлёт шаблон (листы Группы /
Менторы / Ученики) — заполнить и прислать боту тем же файлом.

**Аварийный путь — ручные команды**, если файл не собрать или в нём что-то не
так и разбираться некогда — `/admin_manual`:

```
/add_group Группа A | 2026-08-03 | вечер
/add_mentor +77011112233 Азамат Примеров | Группа A
/add_students Группа A
Сейткали Алия | 10 класс, НИШ
Ли Данияр | 9 класс, НИШ
```

Ещё можно прислать CSV (группа должна уже существовать в базе — образцы в `seed/`:
`mentors.example.csv`, `students.example.csv`).

Дата старта группы — **день 1, понедельник первой недели**. Всё расписание считается
от неё, ничего больше вбивать не нужно. Смена — `утро` (старт 09:30) или `вечер`
(старт 19:00); обе смены учатся по одному и тому же дневному плану, просто в разное
время. Вписать вместо смены другое время — оно сохранится как ручной override только
для этой группы.

Группа, у которой день 9 (хакатон) уже прошёл, считается завершённой и автоматически
скрывается из кнопок выбора группы и из списков (`/groups` без `all` их не покажет) —
чтобы в разгар нового потока не приходилось листать группы прошлых потоков. Полный
список, включая завершённые — `/groups all`.

### Что делает ментор

`/start` → кнопка «Поделиться номером» → он в своей группе. Дальше бот сам пишет первым.

## Расписание

`config/course.yaml` — 9 дней, **две смены в один и тот же день**. Время занятия —
свойство группы (`shift`: `morning` / `evening`), а не курса: обе смены проходят
один и тот же дневной план, просто в разное время.

| День | Смещение | Темы |
|---|---|---|
| 1 | Пн, нед. 1 | Зачем курс? + Знакомство · Дебаты · Claude/Gemini + Google Calendar |
| 2 | Ср | Школьные клубы · Community Service + Интеллект-карта (2 блока) |
| 3 | Пт | Исследования (2 блока) · Ваше исследование |
| 4 | Сб | Спид-дейтинг → MUN (2 блока) · Хакатон + деление на команды |
| 5 | Пн, нед. 2 | Создание своего проекта + MVP · Вайбкодинг · Хакатон Check-Up |
| 6 | Ср | Олимпиады · Летние программы · Прокачка навыков — курсы |
| 7 | Пт | Составление CV · Стажировки (2 блока) |
| 8 | Сб | Презентация исследования · Пицца · Примеры работ → **финальный опрос** |
| 9 | Вс | **Хакатон — защита перед жюри** |

Как считается время:

- **будни (дни 1, 2, 3, 5, 6, 7):** пара 2 часа (`lesson_minutes: 120`), блоки 50 / 50 / 10 минут —
  начала слотов заданы `slot_starts_minutes: [0, 60, 110]`. Утренняя смена — **09:30–11:30**
  (09:30 / 10:30 / 11:20), вечерняя — **19:00–21:00** (19:00 / 20:00 / 20:50).
- **суббота (дни 4 и 8):** обе смены в этот день учатся утром — `start_override: "10:00"`
  у дня перебивает смену группы, шаг между блоками — 60 минут, оба дня 10:00–13:00.
- **воскресенье, хакатон (день 9):** старт 10:00, длительность задана явно —
  `duration_minutes: 180` (10:00–13:00), без расчёта по блокам.

Приоритет начала занятия: `start_override` дня → ручной `lesson_time` группы (редкое
исключение, ставится вручную) → время смены группы (`shifts` в `course.yaml`).
Длительность — явный `duration_minutes` дня; иначе при `slot_starts_minutes` — `lesson_minutes`;
иначе (число слотов в `blocks`) × шаг. Свой `block_step_minutes` или `duration_minutes` у дня
отключает общий `slot_starts_minutes` (так устроены выходные).

Блок может занимать **несколько слотов подряд** — `{name: "Исследования", span: 2}`.
Так у дня 3 «Исследования» идут два блока (там же и про исследовательские программы),
а в субботу MUN занимает два часа. В тексте длинный блок показывается диапазоном:

```
д3  19:00–20:50 Исследования | 20:50 Ваше исследование
д4  10:00–12:00 Спид-дейтинг → MUN | 12:00 Хакатон + деление на команды
```

Слот может быть и `null` — тогда он занимает время (сдвигает следующий блок), но в
тексте не показывается.

Даты не захардкожены: `start_date` группы + `offset_days` дня. Хочешь другой порядок
дней, другое время смен, другой состав блоков — правится в YAML, код не трогается.

Характеристики собираются после дня 9 — то есть уже после хакатона.

## Опрос после урока

Схема из ТЗ: **спрашиваем по исключениям, а не по списку.** Ментор не проходит по
всем восьми с одинаковыми вопросами — он отмечает только отклонения. Про кого
ничего не отмечено, тот и работал ровно: это валидные данные ценой ноль нажатий.

Семь экранов, из них четыре — мультивыбор одним экраном:

1. **Пульс урока** — Отлично / Ровно / Тяжело. При «Тяжело» уточнение уходит в
   методичку, а не в характеристики.
2. **Кого не было** — мультивыбор или «Все на месте».
3. **Кто отличился** — мультивыбор. На каждого отмеченного разворачиваются теги
   (💡 своя идея · 🔍 копал глубже · 🤝 помог команде · 🎤 говорил вслух ·
   ✅ довёл до конца · 📊 принёс данные) и **эпизод одной строкой**.
4. **У кого не шло** — мультивыбор + негативные теги.
5. **Прожектор** — двое за урок, подробно. Кто именно, бот решает сам.
6. **Кто не сдал задание** — мультивыбор.
7. **Итог** — сколько заняло, сколько эпизодов собрано, и красный флаг по тем,
   у кого за курс до сих пор ноль.

Измерено на прогоне (`python -m tools.smoke`, 8 учеников): **11 шагов на урок**,
из них большинство — одно нажатие. Прежняя схема с перебором всех учеников давала
около 40.

### Эпизод — главное, что собирает бот

Дорого в характеристике не «активность 7 из 10», а факт: «переспорил команду и
отстоял свой вариант интерфейса». Через две недели такое не вспомнить. Поэтому
вопрос сформулирован как «что СДЕЛАЛ, а не какой он», и рядом висит подсказка с
примером плохой и хорошей формулировки.

### Ротация прожектора

Двое за урок, по кругу. Приоритет — у кого меньше эпизодов, при равенстве у того,
кто реже попадал под прожектор. За 6 уроков обходит группу из 8 человек, и на
прогоне **ни один не закончил курс с нулём эпизодов** — это критерий приёмки ТЗ.

### Замер по пяти осям

Публичность · Инициатива · Доведение до конца · Глубина · Командность, 0–10.
Дважды за курс: на первом занятии и после хакатона — не каждый урок, иначе
уставший ментор проставит всем одинаковые семёрки. В финале бот показывает
стартовую оценку: «на старте ты поставил 4, что сейчас?», чтобы оценивалось
изменение, а не абсолют. Разница даёт блок «Было → Стало» с цифрами.
Стартовый замер — продолжение опроса дня 1: после вопросов про урок бот сразу
переходит к нему (пока его никто в группе не сделал). В базе это отдельная
сессия `kind='baseline'`, как и раньше.

### Зона роста — это отсутствие проявлений

Правило из ТЗ, реализовано в выгрузке: если за весь курс ни разу не отмечен тег
«Говорил вслух», публичная речь и есть зона роста, независимо от баллов. А
нулевой прирост при высоком старте — стабильно сильная сторона, а не проблема.
Бот выводит оба списка отдельно, чтобы их не путали.

### Воскресный дайджест

Раз в неделю: сколько занятий заполнено, сколько эпизодов, и разбивка
🟢 достаточно / 🟡 маловато / 🔴 пусто. Плюс кто попадёт под прожектор дальше.
Смысл — заметить пустого ученика пока курс идёт, а не когда сел писать
характеристику и обнаружил, что писать нечего.

### Напоминания

Через 30 минут после занятия, затем ещё дважды, если опрос так и не заполнен — ровно
как просит ТЗ. В `config/course.yaml` это часы от конца занятия: `[8, 20]` (то есть
+8 часов и +20 часов от конца конкретного занятия — оно у каждой смены своё, время не
захардкожено). Перед занятием — отдельные напоминания за 120 и 15 минут, с программой
дня и блоками по времени.

### Про «вечный callback и CPU»

Опасение понятное, но здесь его нет. Бот на long polling: держит один HTTP-запрос
к Telegram, который висит до появления апдейта, и **спит** между ними — в простое
это ~0% CPU. Нажатие инлайн-кнопки приходит тем же самым апдейтом, что и обычное
сообщение, и стоит ровно столько же. Никаких циклов ожидания в коде нет.

Единственная фоновая задача — тик планировщика: несколько SELECT'ов по Postgres и сон.

## Голосовой ввод

`STT_PROVIDER` в `.env`:

- `faster_whisper` — локально, бесплатно. Модель грузится лениво при первом
  голосовом, распознавание уходит в отдельный поток и не блокирует бота.
  Отдельный ffmpeg не нужен — PyAV внутри пакета читает `.oga` от Telegram сам.
- `openai_compatible` — удалённый `/v1/audio/transcriptions`.
- `off` — только текст.

### Замеры на этой машине (CPU, int8, русская речь)

| Модель | Скорость после прогрева | Качество |
|---|---|---|
| `tiny` | ×22 реального времени | текст понятен, имена в мусор |
| `small` | ×4–5 реального времени | рабочее качество, спотыкается на именах |

`small` стоит по умолчанию: 16-секундная заметка распознаётся за 3–4 секунды.
Первый запуск дольше — скачивается модель (~460 МБ) и грузится в память.
`beam_size` поднимать бессмысленно: проверял 5 против 1 — текст тот же, время +40%.

### Имена и термины

Whisper плохо берёт казахские имена. Две меры, обе в `app/stt.py`:

**Словарь-подсказка.** Бот знает состав группы и передаёт имена учеников плюс
термины курса (`stt_vocabulary` в `config/course.yaml`) в `initial_prompt`.
Порядок в промпте не случайный: faster-whisper обрезает его до последних ~224
токенов, поэтому имена идут в конец. Что это дало на тесте:

```
без словаря:  Адея сегодня наконец разговарилась
со словарём:  Алия сегодня наконец разговарилась
без словаря:  Даньяр держал тайминг
со словарём:  Данияр держал тайминг
```

**Починка смешанных алфавитов.** Whisper выдаёт «МUN» — кириллическая М плюс
латинские UN. `normalize_terms()` чинит такие слова, но трогает только те, где
намешаны оба алфавита И где после замены получился термин из словаря. Обычное
слово так задеть нельзя — в русском тексте смеси алфавитов не бывает.

**Что не чинится.** «Аружан отвлекалась» упорно распознаётся как «оружие
отвлекалось» — слишком похоже на частотное слово, словарь не перебивает.
Нечёткую автозамену по именам я делать не стал: похожесть «оружие»/«Аружан» —
0.50, на таком пороге замена начнёт портить настоящие слова, а это хуже опечатки.

На деле это почти не мешает: заметки по ученику бот и так подшивает к нужному
человеку — он сам спрашивает про каждого по имени, и привязка не зависит от того,
расслышал ли Whisper имя внутри реплики.

### Как отвечают на вопросы

Бот смотрит на тип сообщения и сам решает, что с ним делать: текст сохраняет как
есть, голосовое отправляет в расшифровку. Кнопочные вопросы (шкалы, выбор
варианта) принимают и нажатие, и ответ текстом — «4» или «Опоздал» сработают
так же, как кнопка.

**После голосового ответ сохраняется сразу**, а под расшифровкой висит кнопка
«↩️ Переписать». Так сделано осознанно: обязательное «сохранить? да/нет» — это
+1 нажатие примерно пятнадцать раз за один чек-лист (12 учеников плюс заметки по
группе), при том что расшифровка обычно нормальная. В хорошем случае кнопка стоит
ноль действий, в плохом — одно, ровно как «нет». Плюс она живёт на старом
сообщении: заметил кривую расшифровку на седьмом вопросе — вернулся и переписал
третий, опрос при этом не сбивается и продолжится с того же места.

Подтверждение всплывает само, когда есть повод. Поводов два:

- **whisper не уверен** — `avg_logprob` ниже порога;
- **расшифровка оборвалась** — слов заметно меньше, чем должно быть для такой
  длительности записи. Второй признак появился после замеров: при плохом звуке
  whisper с включённым VAD чаще обрывает распознавание или отдаёт пустоту, чем
  выдаёт неуверенный текст, и одной уверенностью такой случай не поймать.

Совсем пустую расшифровку бот не сохраняет вовсе — просит записать заново или
написать текстом.

Режим переключается в `config/course.yaml`:

```yaml
voice:
  confirm: smart          # always — спрашивать всегда (надёжнее, но +1 нажатие
                          #          на каждый голосовой)
                          # smart  — только когда есть повод (по умолчанию)
                          # never  — не спрашивать, править кнопкой
  low_confidence: -0.6
  min_words_per_sec: 0.6
```

Порог `low_confidence` — значение с запасом, а не откалиброванное: чистая речь на
замерах даёт -0.22, а правдоподобно-плохую запись синтезировать не вышло (белый
шум VAD просто вырезает целиком). Запиши несколько настоящих заметок, посмотри
числа через `tools/test_stt.py` и подвинь порог под свои условия.

### Проверить у себя

```bash
python -m tools.test_stt голосовое.oga --names=Алия,Данияр,Аружан
```

Прогонит файл дважды, без словаря и с ним, и покажет текст, время, скорость и
уверенность — по ней и настраивается порог `low_confidence`.
Где взять `.oga`: записать голосовое в Telegram и сохранить его как файл.

### Если захочется распознавать через Alem

Эндпоинт `/v1/audio/transcriptions` на `llm.alem.ai` живой, но ключ выдаётся под
конкретные модели — проверено запросом:

```
401 key not allowed to access model. This key can only access models=['qwen3-8']
```

Значит, нужен **отдельный ключ** с доступом к модели Speech-to-text (в каталоге
Alem есть обычная и казахская). Дальше `STT_PROVIDER=openai_compatible`,
`STT_API_KEY=<новый ключ>`, `STT_MODEL=<имя модели из консоли>` — код готов,
менять ничего не надо, подсказка словаря уйдёт туда же в поле `prompt`.

Сам `qwen3-8` — текстовая модель, звук она не принимает: её дело — черновик
характеристики, а не транскрибация. Поэтому **слушает whisper, пишет qwen3-8**.

## Материалы для характеристик — основной путь

`/export` → бот присылает два файла.

**Общий HTML** — все ученики в одном документе. По каждому:

- шапка с цифрами: посещаемость, средняя включённость и её динамика (спарклайн по
  дням), сколько раз отмечен как вытягивающий или выпадающий;
- блок «Материал по разделам характеристики» — под каждым заголовком синим написано,
  **в какой раздел документа он идёт**: сильные стороны → раздел 03, было → стало →
  раздел 04, зона роста → 05 и так далее;
- блок «Наблюдения по дням» — сырые заметки с занятий, откуда берутся конкретные
  примеры;
- предупреждения, если по ученику нет заметок или не заполнен финальный опрос.

**ZIP** с тем же самым в четырёх видах:

```
svodnaya_tablica.csv   посещаемость и включённость по группе, для Excel
vse_ucheniki.html      то же, что бот прислал отдельно
ucheniki/*.md          по файлу на ученика — копировать куски в документ
syrye_dannye.json      всё машиночитаемо
КАК_ПОЛЬЗОВАТЬСЯ.txt
```

Всё это делается **без всякой модели** — только сбор, группировка и подсчёты.
Что куда ложится, задаётся полем `maps_to` в `config/questions.yaml` и таблицей
`SECTIONS` в `app/dossier.py`.

## 🧪 Автосборка характеристик — эксперимент

Выключена по умолчанию: `EXPERIMENTAL_CHARACTERISTICS=true` в `.env`, тогда в меню
появится «🧪 Характеристики» и команда `/characteristics`.

Что делает: заметки по ученику + контекст по группе → в LLM с жёсткой инструкцией
«ничего не выдумывать, опираться только на заметки» → JSON по схеме из 11 разделов →
`templates/characteristic.html.j2` → файл.

Почему эксперимент: модель может переставить акценты, приукрасить или сгладить
неудобное — а документ идёт родителям. Каждый черновик надо перечитывать. Раздел 11
(«Что меняет сопровождение») статический, разделы 01–10 генерируются.

При `LLM_PROVIDER=off` или если модель не ответила — придёт черновик с сырыми
заметками. Ничего не теряется.

### Что выяснилось про qwen3-8 на llm.alem.ai

- Модель **reasoning**: на каждый ответ тратит скрытые размышления
  (`reasoning_content`), и они едят тот же бюджет `max_tokens`. На односложное «Да»
  ушло 247 completion-токенов.
- Отключить размышления **не получается**: `chat_template_kwargs:
  {enable_thinking: false}`, `enable_thinking` в теле и `/no_think` в промпте —
  проверены все три, `reasoning_content` приходит всё равно.
- Поэтому один запрос на всю схему из 11 разделов упирался в лимит:
  `finish_reason: length`, а `content` приходил обрезанным или вовсе `null`.
  На двух запросах спотыкался второй. Сейчас генерация разбита на **три запроса**
  (что было на курсе / портфолио и цель года / дорожная карта) — так проходит
  целиком. Если один сорвётся, остальные уже собраны: документ придёт неполным,
  но не пустым.
- Сеть на длинных генерациях иногда рвётся — на каждый запрос есть один ретрай.
- `response_format: {"type": "json_object"}` эндпоинт поддерживает.
- Упёрлись в лимит снова — поднимай `LLM_MAX_TOKENS`, бот скажет об этом прямым
  текстом, а не молча отдаст мусор.

## Перенос на сервер (Linux)

Оба бота — long polling, вебхук не нужен, сами по себе публичный IP/домен/
HTTPS-сертификат им не нужны. Ботам достаточно исходящего интернета до
`api.telegram.org`.

Но переносятся они не отдельно и не на Vercel. Сайт (корень репозитория —
воркбук ученика, mentor view) и оба бота едут **вместе, на один VPS** — это
не тот случай, где часть проекта можно спокойно оставить в serverless:

- SSE-стримы веб-платформы (`/api/workbook/<id>/stream`,
  `/api/mentor/groups/<id>/stream`) и `LISTEN/NOTIFY` в Postgres требуют
  одного длинно живущего процесса рядом с базой — как раз то, чего
  serverless-функции Vercel не дают.
- Персональные данные детей по закону РК должны храниться на территории
  Казахстана — общий Postgres с воркбуком и ботами должен физически стоять
  в Казахстане, а не там, где решит развернуть его серверлесс-хостинг.

Маркетинговый лендинг (если он когда-нибудь станет самостоятельным и не
будет зависеть от того же Postgres) в принципе может остаться на Vercel
отдельно — но сама платформа (воркбук, mentor view), Postgres и оба бота
живут на одном KZ VPS. Полный порядок разворачивания — `deploy/README.md`
в корне репозитория; этот раздел — только про сами Python-процессы ботов.
У бота свой хост нужен только под сами процессы — и под тот же
`DATABASE_URL`, что видит веб-платформа: это общий Postgres, а не
что-то бот-специфичное для переноса.

Обычного git хватает — секреты и машинно-зависимое уже в `.gitignore`
(`.env`, `.venv/`, `data/`). Роль, которую раньше играла отдельная SQLite-БД,
здесь у Postgres: если это тот же инстанс, что уже видит прод-сайт (или его
реплика/дамп на новом сервере), группы/менторы/ученики можно и не гонять
заново — они уже там. Нужен именно свежий инстанс — тогда `/sync_sheet` (и
ночной автозабор) восстановит ростер из Google-таблицы; накопленные заметки/
чек-листы/фидбек от детей/хакатон-команды из таблицы не восстановятся —
только `pg_dump`/`pg_restore` самого Postgres.

### Разово на сервере

```bash
git clone <URL-репозитория> /opt/prime-teens
cd /opt/prime-teens/bot

python3.14 -m venv .venv
.venv/bin/pip install -r requirements.txt

cp .env.example .env
nano .env   # BOT_TOKEN, KIDS_BOT_TOKEN, DATABASE_URL и т.д. руками — .env в git не попадает
```

`DATABASE_URL` должен указывать на тот же Postgres, что и сайт (либо на его копию
для этого сервера) — схему и миграции по-прежнему ведёт Prisma из корня репозитория
(`pnpm prisma migrate deploy`), бот сам ничего не создаёт.

`.env` на сервер копировать НЕ через git — впиши значения руками (выше) или
перекинь файл отдельно по `scp` (разовая передача секрета по защищённому каналу,
не хранение в репозитории):

```bash
scp .env primeteens@<сервер>:/opt/prime-teens/bot/.env
```

Проверь руками, что оба бота стартуют и не падают:

```bash
.venv/bin/python -m app.main       # Ctrl+C, когда увидел, что поднялся без ошибок
.venv/bin/python -m app.kids.main  # аналогично
```

### Автозапуск и автоперезапуск (systemd)

В [`deploy/`](deploy/) — два юнит-файла, `primeteens-mentor.service` и
`primeteens-kids.service`. Перед установкой поправь в них `User=` и
`WorkingDirectory=`/`ExecStart=` под реальные путь и системного пользователя (не
рут — создай отдельного: `useradd -r -m primeteens`, и отдай ему `chown -R` на
`/opt/prime-teens`).

```bash
sudo cp deploy/primeteens-*.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now primeteens-mentor primeteens-kids
```

Логи:

```bash
journalctl -u primeteens-mentor -f
journalctl -u primeteens-kids -f
```

### Обновление кода

```bash
cd /opt/prime-teens
git pull
cd bot && .venv/bin/pip install -r requirements.txt   # если requirements.txt менялся
sudo systemctl restart primeteens-mentor primeteens-kids
```

### На заметку

- Python 3.14 — та же версия, на которой проверялись колёса `faster-whisper`/
  `ctranslate2` (см. `requirements.txt`). Более новый Linux-дистрибутив вполне
  может тащить только 3.11–3.12 из коробки — тогда ставь 3.14 отдельно
  (`deadsnakes` PPA на Ubuntu, или pyenv) либо проверь, что на доступной версии
  колёса тоже есть, прежде чем переносить.
- `data/media`, `data/out` создаются сами при первом запуске
  (`Path.mkdir(parents=True, exist_ok=True)` в `app/config.py`) — руками заводить
  не нужно.
- Не запускай оба бота одновременно на старой (Windows) и новой (сервер) машине —
  два процесса с одним `BOT_TOKEN` дерутся за `getUpdates`, это уже приводило к
  дублирующимся/потерянным сообщениям в этом проекте. Останови `run.bat`/
  `start_both.bat` на Windows, прежде чем поднимать `systemctl start` на сервере.

## Данные и приватность

БД — Postgres, общий с веб-платформой (`apps/web`); данные бота (группы, ученики,
менторы, ответы чек-листов) лежат в тех же таблицах, что видит платформа, но своих
экранов для них платформа пока не показывает. Тесты (`tools/test_*.py`, `smoke.py`)
не трогают эту базу — `tools/_pgtest.py` гоняет их на отдельной `primeteens_test`,
создавая/мигрируя/очищая её перед каждым прогоном.

Телефон ментора хранится только чтобы сопоставить его со списком; телефоны учеников
бот не собирает вообще. Заметки менторов — персональные данные несовершеннолетних.

Выгрузка `/export` работает целиком локально: наружу не уходит ничего. Заметки
покидают машину только в двух случаях — если включено распознавание голоса через
удалённый STT и если включена 🧪 автосборка характеристик. Не устраивает —
`STT_PROVIDER=faster_whisper` (локально) и `EXPERIMENTAL_CHARACTERISTICS=false`.

Голосовые удаляются с диска сразу после расшифровки.
